## What is wrong, cited at origin/main

`maintain()` builds each statement with `format!` and runs it through
`db.execute(&sql, ...)` or `db.query_row(&sql, ...)`. Both prepare a fresh statement,
run it, and drop it. Per maintained row.

| file | fresh-prepare call sites |
|---|---|
| `src/1_maintenance.rs`, the `maintain` path | 7 |
| `src/1a_relational.rs` | 19 |

## The idiom is already in this repo

`rusqlite` keeps an LRU of prepared statements keyed by SQL text. Seven sites already
use it: `src/1a_relational.rs:26`, `:69`, `:133`, `:217`, `:871`, and
`src/2_vtab.rs:138`, `:302`. Follow those, do not invent a second pattern.

The SQL text is stable per view per step, so the cache hits. The `format!` rebuild
costs an allocation and does not defeat the cache; hoisting it is a smaller second win
and is optional in this lane. If you do it, say so separately.

## The bound

`rusqlite`'s statement cache has a capacity and it is not unlimited by accident. State
the capacity you set and what it protects, as a named constant with a comment. A cache
whose capacity is smaller than the number of distinct statements per fold thrashes just
as badly as no cache, and it does it silently. Prove the capacity covers the corner in
the verdict.

## Style laws

- Comment budget: only constraints the code cannot show. No change-log narrative,
  no dates, no arc references.
- `eprintln!` never in `src/**`. `tracing` only.
- Every loop and recursion carries an explicit budget and a named diagnostic when the
  budget is hit. The bound is a constant with a comment saying what it protects.
- Colocated consistency: inside a file, follow that file's style.
- No em dashes. Banned in prose and identifiers: provenance, substrate, load-bearing,
  regime, "ground truth" (say oracle), refusal. "support" is banned, use refCount.
- Never a per-row write.
