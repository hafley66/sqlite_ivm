## What the lab must answer

Today every `xUpdate` runs the whole maintenance query inline: `DELETE FROM
<view>_delta`, an insert of contributions, then a `GROUP BY`. Per row. An UPDATE
pays it twice, once for OLD and once for NEW (`src/1_maintenance.rs:388`).

The shape being tested: buffer in `xUpdate`, flush in `xSync`. The maintenance
query then runs once per transaction instead of once per row.

## The design is already answered by precedent. Do not redesign it

| question | FTS5's answer | site |
|---|---|---|
| where does the flush go | `xSync` | `fts5.c:21203` |
| what about `xCommit` | no-op, with a comment saying why | `fts5.c:21215` |
| how is the buffer bounded | byte cap, 1 MiB default, tunable | `fts5.c:4548`, `:16326` |
| savepoints | flush on savepoint and release, discard on rollback-to | `fts5.c:22248`, `:22265`, `:22283` |

`rusqlite::vtab::TransactionVTab` at `vtab/mod.rs:356` exposes begin/sync/commit
and sqlite_ivm implements none of them. That trait is your seam. There is no
statement-end hook for a vtab, so the transaction is the only batch boundary
available; do not go looking for a finer one.

Background reading already in tree: `docs/2026-09-19-fts5-clock-choices.md` and
`docs/2026-09-19-vtab-clocks.md`. The second is stale (it lists eight steps from
the removed JSON-payload design against today's nine). Trust the first.

## The bound is mandatory

An unbounded buffer is a blocking defect under the every-loop-is-bounded law.
Byte cap as a named constant with a comment saying what it protects, plus FTS5's
second trigger: flush when ordering breaks. An untested cap is decoration.

## Test plan, already written. Follow it

What breaks if wrong: rows buffered and never flushed, or flushed twice, or a
rollback leaving them in. Each is a wrong answer that looks like a fast one.

| case | input | expected | why it exists |
|---|---|---|---|
| batching | 100 inserts in one transaction | maintenance statements constant, not 100x | the claim, as a `CountRecorder` assertion |
| rollback | inserts then ROLLBACK | no flush, view unchanged | a buffer that flushes on rollback invents rows |
| savepoint | SAVEPOINT then RELEASE | flushes | `fts5.c:22248`, `:22265` |
| rollback-to | SAVEPOINT then ROLLBACK TO | discards | `fts5.c:22283` |
| early flush | more than the byte cap in one transaction | flushes mid-transaction, answer still correct | an untested bound is decoration |
| update pays twice | one UPDATE | both OLD and NEW buffered | `src/1_maintenance.rs:388`; coalescing them silently drops a retraction |
| xCommit is inert | any transaction | nothing failable in `xCommit` | SQLite discards its return code, so a failure there is silent |

Untested and why: wall time, and concurrent writers. SQLite is single-writer, so
the second is not a case.

**The trap:** a buffer that passes every case above by flushing on every `xUpdate`
anyway. The `CountRecorder` assertion in row one is the only thing that catches it.
