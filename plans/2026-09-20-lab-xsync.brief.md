## The change

Buffer in `xUpdate`, flush in `xSync`. `src/2_vtab.rs` appends; the maintenance work
runs once per transaction instead of once per row, which is what makes the three
prepared statements reusable instead of re-prepared.

This is not a new design. FTS5 does it in tree. Every site is in
`docs/2026-09-19-fts5-clock-choices.md`:

| question | answer | site in the local amalgamation |
|---|---|---|
| where does the flush go | `xSync` | `fts5.c:21203` |
| what about `xCommit` | no-op; SQLite discards its return code | `fts5.c:21215` |
| how is the buffer bounded | byte cap, 1 MiB default, plus an ordering trigger | `fts5.c:4548`, `:16326` |
| savepoint, release | flush | `fts5.c:22248`, `:22265` |
| rollback-to | discard | `fts5.c:22283` |

Read that document before writing the buffer.

## Two rails

**The bound is mandatory.** An unbounded buffer is a blocking defect under the
every-loop-is-bounded law. Named constant, a comment saying what it protects, and an
early-flush test that actually trips it.

**The trap.** A buffer that passes every correctness test by flushing on every
`xUpdate` anyway. Write the `CountRecorder` assertion first, before the buffer, so it
fails before it passes.

## Style laws

- Comment budget: only constraints the code cannot show. No change-log narrative,
  no dates, no arc references.
- `eprintln!` never in `src/**`. `tracing` only.
- Every loop and recursion carries an explicit budget and a named diagnostic when the
  budget is hit. The bound is a constant with a comment saying what it protects.
- Colocated consistency: inside a file, follow that file's style.
- No em dashes. Banned in prose and identifiers: provenance, substrate, load-bearing,
  regime, "ground truth" (say oracle), refusal. "support" is banned, use refCount.
- Never a per-row write.
